# Isolated publication and recovery

Verify the existing publication boundary against an explicitly approved synthetic
tracker target. Default offline verification grants no write authority.

## Sub-features

- F6.1: Resolve the approved test workspace, team, project, source revision, spec revision, effects and object limit before writing; inspect existing records across statuses first.
- F6.2: Publish only the approved synthetic spec and test issues through native controls, then save one justified blocker and read back every record and both relation directions.
- F6.3: A fresh missing-receipt handoff searches by source, meaning and title, recovers the existing canonical record including a canceled match, and neither duplicates nor revives it.
- F6.4: Return actual URLs, saved fields, criterion coverage and observed limits. Preserve draft PRs, the real pilot, readiness and execution authority.

## How to get to it (user POV)

Ask to qualify publication on a dedicated synthetic project after separately
approving its exact effect boundary. Read the product's
[publication owner](../../../../config/agents/plugins/personal/library/delivery-slice/references/publication.md)
and the current approval receipt. A prior test approval is not standing permission
to create another project or more records.

## Driving it with native tracker controls

Preconditions: Launch/Doctor pass; the current user explicitly approves a test-only
project, synthetic spec, at most three test-only issues, one native blocker and
the third fixture's cancellation for the cross-status recovery case.
Use the foreground writer and existing signed-in native tracker route. Record
the actual source version and approval. No real delivery tasks are part of this
journey. If the isolated target or approval is absent, report blocked.

- Inspect the destination and search matching source/title/meaning across all
  statuses. Reuse the exact authorised target instead of blindly recreating it.
- Use `branch.md` and an actual candidate-produced spec/ticket draft as synthetic
  inputs. Keep fixture outcome acceptance, draft review and test-write authority
  distinct. Preserve source revision 3 separately from `SPEC-DRAFT r1`.
- Create the test spec and two complete synthetic slices only within the approved
  target. Verify project, status, kind, assignee, source links, criteria and limits
  in the native form before submitting. Capture saved identities, not draft aliases.
- Save the first-slice-blocks-second relation with the tracker's native operation.
  Reload both issues and verify `Blocking` and `Blocked by`; body links alone fail.
- Prepare the recovery fixture through its separate `linear-intake` owner,
  within the approved third-record allowance. Capture a synthetic idea in native
  Triage with `kind/idea` and read it back. Record the authorised cancellation
  of only that test idea for cross-status lookup; preserve its canceled state.
  This fixture preparation is not delivery-slice intake ownership.
- Give a fresh read-only session the intended project, original idea and source,
  but withhold the earlier saved-record receipt. Require source/meaning/title
  search across statuses, canonical existing-record recovery and no retry write.
  This is a missing-receipt recovery test, not an injected transport failure.
- Compare actual saved records, native relation and counts against the authorised
  effects. Retain prompts, native observations, timestamps, identities, readback,
  screenshot proof and evidence after cleanup. Leave synthetic records clearly
  marked and report their actual final states; deletion needs its own authority.

## Gotchas

A foreground writer applying the candidate instructions qualifies that user path,
not autonomous native-catalogue publication. An explicit-source desktop session
qualifies only its observed behavior. Keep the source-loading and capability
distinctions in the [native reference](../../verify-ecosystem-review/references/native-capabilities.md).
Observed no-write behavior is not a complete remote audit or a global enforcement
guarantee. A known saved object with a withheld receipt does not reproduce a
provider timeout or a failed relation write. Report those fault-injection paths
unrun unless an existing supported isolated mechanism actually exercises them.
