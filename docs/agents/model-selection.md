# Model selection at startup

Apply this policy before starting, resuming or changing a coordinator or worker
in Herdr or Herdr Projects. Keep provider-specific configuration and discovery
in its owning plugin, reached through the installed skill.

## Bind the request

- Preserve an explicit model, provider, account and reasoning effort as
  independent requirements. A model name alone does not select its provider.
- Resolve the execution host, exact Herdr and Herdr Projects executable paths,
  and their installed versions and help before choosing launch syntax. Distinguish
  the legacy project/thread CLI from the native task-board CLI by that evidence.
- Keep execution placement separate from inference routing. A remote model does
  not give a local agent remote files, tools or permissions.
- Apply the task's privacy and account boundaries. An exclusive employer route
  stays exclusive. Otherwise inspect both authorized personal and employer
  routes before reporting that the requested model is unavailable.

## Establish availability

- Use the provider plugin's canonical discovery route for employer models.
  Compare its catalogue with the full live Azure deployment inventory on the
  configured resources when a requested model is missing. Read only deployment
  identity, model and provisioning state; keep tenant and resource details in
  their private owner.
- Inspect the personal native harness's account status and current model
  inventory. When using its model cache, check freshness and read only model
  entries and timestamps. Keep credentials and secret values out of output.
- Treat an absent catalogue label or stale cache entry as a discovery gap.
  A live deployment can exist while the launcher cannot select it. Report
  deployment availability and route qualification separately.
- Preserve the exact requested model when discovery or launch fails. Report
  the failing route and repair owner; obtain a decision before substituting
  another model or a provider outside the request's authority.
- For unspecified choices, use the owning workflow's current model guidance
  and the inspected routes. Record the chosen model, provider, account and
  effort before launch. Keep live model lists out of these instructions.

## Verify the actual session

- Use the selected provider's supported launcher and the installed Herdr or
  Herdr Projects contract. Inspect the effective role or task settings,
  including fallback settings, so a fallback cannot silently change the request.
- Verify the resulting execution host, native harness, session identity, model,
  provider, account, effort and working directory. Use native session metadata
  and redacted launcher evidence; a profile label or successful spawn is
  insufficient.
- Require a completed harmless first turn through the selected route before
  reporting it as running on that model. Keep selected, spawned, ready and
  first-turn verified distinct. Report any identity field still unknown.

## Change an existing session

- Reach a safe turn boundary and preserve the current task, conversation,
  worktree and unfinished work before changing model or effort.
- Use the native same-session change when supported. Verify the effective
  settings and next completed turn. If that route cannot preserve the work,
  prepare a handoff and obtain authority for replacement before restarting.
- Keep source policy edits, installed configuration and fresh-startup behavior
  as separate proof states. A documentation change proves only the first.
