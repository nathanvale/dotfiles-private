# Draft and edit custody

The recipient sees the requested handoff, while Nathan's edits and publication
authority remain intact.

## Sub-features

- `draft-complete`: each requested artifact has a verified link or declared gap.
- `edit-preserved`: a revision preserves unrelated text, links and mentions.
- `draft-unsent`: verification returns a draft without changing remote state.

## How to get to it (user POV)

Request a new handoff announcement, correct a missing link, or revise an existing
post. Start from the actual current post for an edit, not an older local copy.

## Driving it with the service owner

Preconditions: identify the intended recipient, existing post where applicable,
requested change, publication owner and current authority.

- **Read.** Use the service owner's supported readback for the current message.
  Retain Nathan's latest additions and verified mention identities.
- **Compare.** Save a local unsent proposal and compare its changed passages with
  the requested change. Account for every requested package, preview and guide;
  a receipt does not stand in for a requested interactive review.
- **Preserve.** Keep unrelated passages, links and mentions. Reuse settled exact
  approval within its scope; route changed scope through the existing owner.
- **Return.** Present one exact draft with recipient, limits and next action.
  Keep missing delivery proof outside the copy. Leave it unsent and record that
  no remote edit was made. Publication follows the service owner's authority
  and saved-text/link readback contract, with one publisher.

## Gotchas

Drafting and verification grant no send or deployment authority. A reply, a new
channel post and an edit are different destinations. Preserve a prepared human
draft; do not replace it while checking links. A queued action is not a saved post.
