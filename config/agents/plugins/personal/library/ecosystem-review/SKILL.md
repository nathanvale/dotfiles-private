# Review the agent ecosystem

## Resolve the current map

Enter through `$HOME/.config/context/vault.md` and the startup pointer for
agent ecosystem planning. Follow the current planning note's live entry and
cutover ledger to the initiative's source index. Verify the workspace and
project from current records. The index owns the map and document addresses;
keep account IDs and the ecosystem plan out of this skill.

Prefer connected Linear tools. If they lack a required read, use the current
Harness's supported browser controls and the existing signed-in personal
session, following its browser owner. Report an unavailable route precisely.
Use existing integrations and credential custody rather than adding a client,
connection, permission, or orchestrator.

If the user supplies records for an offline review, treat them as the bounded
source set and label the result offline. They do not establish current Linear
state. Retained local notes are context until refreshed against their owners.
When live access is unavailable, use the closest saved summary and name the
unread owners. Avoid loading full historical archives to fill that gap.

For missing live reads, distinguish a task-imposed restriction from an absent
capability, authentication failure, or unread source. Use actual tool discovery
or a supported read attempt to substantiate the limitation. When the current
decision frontier is unread, recommend the access or evidence repair first.
Describe saved open choices conditionally instead of asking Nathan to decide
them again as though their current state were known.

## Read across the outcomes

Read the whole root map, the proposed Now / Next / Later overview, and the
living ecosystem glossary. Read the task-engine glossary when that branch
needs interpretation. Follow each outcome to its owning issues, including
current questions, accepted-answer comments, assignment, native blocker
relations, and relevant recent updates or intake. Cover every outcome without
loading full archives or inventorying the machine.

Follow source, PR, native-task, and qualification receipts selectively when a
claim, decision, contradiction, or completion needs support. Keep these states
distinct: proposed, accepted, implemented, merged, installed, activated, and
runtime-qualified. A Done status or closed predecessor does not prove a usable
outcome. Identify the environment, revision, and date a receipt actually proves.

Separate native blockers from parent-child decomposition, architectural links,
and proposed prerequisites. Keep accepted answers settled unless new evidence
contradicts them. Where an older description conflicts with a later accepted
answer, cite the answer and flag the stale summary. Preserve open human choices
and proposed ordering.

Compare changes only against a supplied previous review or an explicit time
window. Identify that baseline and any missing comparison evidence. Without a
baseline, call the result a current snapshot. For a time window, state its dates
and timezone and use dated events or source revisions. An updated timestamp
alone does not establish which facts changed. Create no review-history store.

## Recognize the delivery stage

Read the source index's "Idea to delivery: how the four skills fit together"
section for workflow ownership. Trace relevant intake receipts, accepted
outcomes, spec versions and acceptance checks, proposed tickets and coverage,
publication approvals, and linked native execution evidence. Retain the observed
intake, outcome, spec, criterion and ticket identities and their coverage links
in the briefing. A compact mapping is enough; create no new spec or tickets.

Distinguish outcome acceptance, spec acceptance, ticket publication, execution
authorization, merge, and activation. Report missing proof as a gap, rather
than inferring that no work exists. Planning status is not runtime state.

When the next step is a spec or ticket plan, recommend a source-linked handoff
to `delivery-slice`. Name the bounded outcome, accepted-decision sources,
constraints, exclusions, and material open choices it needs. Link the workflow
owner separately from the outcome or spec records: resolve `delivery-slice` in
the current Harness catalogue and link its actual installed `SKILL.md` directly
in the recommendation. Confirm that target exists. A planning-record link alone
does not complete the handoff; if the skill cannot be resolved, report the
missing workflow pointer and its installer owner. Leave spec and ticket writing
to that owner; do not invoke it during a review. Keep unrelated fog open.
Ecosystem review is optional orientation, not a compulsory gate.

## Carry a small Markdown handoff

Read the source index's "Small Markdown handoff contracts (accepted)" section
for the current information contract. Accept canonical planning pointers,
optional comparison inputs, or bounded supplied records. Return an overview,
open questions, and a source-linked next-owner recommendation in chat.

Carry source revision or observation time, scope, privacy and exclusions,
evidence gaps and their consequences, and the next responsible owner. When an
allegedly existing acceptance is inaccessible or
conflicting, recommend its decision owner recover the canonical answer. A clearly
unaccepted draft awaits human review, not recovery of a prior acceptance. Keep
source branch revision distinct from spec draft revision.
Point to accepted facts in their existing owners rather than copying a decision
store. Mark incomplete access or unresolved evidence as partial, with the repair
route. A review grants no drafting, publication, readiness, or execution authority.
A direct accepted-outcome handoff to delivery-slice needs no preceding review.
Exact headings, shared-definition placement, and machine validation remain open.

## Return a two-minute briefing

Lead with one plain assessment and the useful outcomes actually proven.
Represent all outcome horizons, visibly retaining proposed ordering. Combine
related outcomes only when each remains identifiable.

Include:

- Linked evidence for the material claims, with freshness and coverage. Use
  literal absolute paths with optional `:line` for local sources. Keep invisible
  formatting controls and heading fragments out of local link targets so chat
  can open the actual file. Confirm local targets exist before returning.
- The operation currently authorized and its approval reference. For a handoff,
  explicitly state whether drafting authority was supplied. Keep publication,
  readiness, and execution authority separate; a recommendation grants none.
- Real blockers, their direction, and the work they prevent.
- Human choices separately from facts needing investigation.
- One recommended next decision or action and why it matters. Leave acceptance
  to Nathan.
- Missing, stale, inaccessible, or conflicting evidence and its effect on the
  conclusion. Label incomplete access a partial review, never an empty backlog.

Keep the briefing compact. Avoid health scores or progress percentages without
an independently supported denominator. When access prevents an outcome count,
state that limit rather than inventing coverage or conclusions.

Return in chat by default. Saving, posting, priority or status changes,
architecture decisions, research launches, and task dispatch are separate
operations. Route requested capture or triage to `linear-intake`; route
requested consequential decision exploration to Wayfinder through the current
planning owner. A review grants no mutation authority.
