# Publication boundary

Resolve the exact approved spec revision, ticket breakdown and requested effects
before a write. Use the project's native planning vocabulary and privacy owner,
not the starting repository's tracker defaults. Recheck the actual workspace,
team, project and canonical spec/delivery owner against live records.

Use existing connected tracker tools or the Harness's supported browser route.
If the required capability is absent, return the drafts and missing operation;
leave credentials and integration setup with their owners. Never invent a client.

Search by source, meaning and title across all relevant statuses, including
completed and canceled records. Inspect matches and reuse canonical records
where appropriate. Changed acceptance or scope returns to review. Publish only
the authorized spec and approved tickets, blockers first, then wire the native
blocking relations. Grouping under a parent does not implement blockers.
Keep statuses, assignments and readiness within explicit write scope; a label
never grants dispatch authority. Publication supplies no implementation approval.

Read back every saved record and relation. Return actual URLs, revision,
criterion coverage, verified effects, partial outcomes and remaining failures.
On an unknown mutation outcome, inspect the exact target before retrying. Stop
when its identity or outcome cannot be established; record the inspection needed
for recovery instead of duplicating a write. Do not close or rewrite the decision
branch as delivered because its spec or tickets now exist. Leave execution,
review and recovery to the adopted native task owner.
