# Verify native harness access

Check the same harness, configuration directory, and process that will run work.

## Sub-features

- `harness-codex` covers native Codex status and one authorized request.
- `harness-claude` covers native Claude Code status and one authorized request.

## How to get to it (user POV)

Use the intended Codex or Claude Code shell. Keep its native auth owner.

## Driving it with the native harness

Preconditions:

- The doctor admitted the expected account home and transport hint. If normal
  login-Keychain metadata is blocked, the native owner's independently verified
  storage preconditions can admit this separate journey. Retain that blockage.
- The task authorizes the native auth check and bounded real request.

1. Read [native routing](../../credential-custody/references/native-harness.md).
2. In Codex, run `codex login --help`, then its supported `status` command.
   In Claude Code, run `claude auth --help`, then its supported `status` command.
   Capture privately and retain only the required status and context.
3. Execute one task-authorized harmless request through that same harness.
   Require the actual result. Record provider, profile, source revision, and
   process context without credentials.

## Gotchas

- Another harness's success is a different entry point.
- An intentional private config directory may use separate custody.
- Status does not prove a real provider request. No native auth or request is
  part of the metadata-only journey.
