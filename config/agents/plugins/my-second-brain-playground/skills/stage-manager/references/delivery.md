# Coordinate for delivery

Apply this policy within the selected coordinator's existing role and authority.
Use the project's adopted task, knowledge and execution owners.

## Deliver the current task

- Keep one named delivery outcome and its acceptance evidence visible.
  Define completion through an observable result, not a worker's exit or claim.
- Delegate bounded implementation and independent review. Give each worker its
  scope, acceptance, stop condition and source pointers. Keep conversation,
  decisions and handback acceptance with the coordinator; answer small read-only
  questions directly.
- Read the relevant decision and evidence pointers before dispatch or a material
  decision. Pass pointers and the new delta instead of copying transcripts or
  whole project histories into briefs.
- Choose skills for the current gap. When the route is unclear, consult the
  installed `ask-matt` router and read only the selected skills. Pass relevant
  execution skills to the worker; keep coordination and acceptance here.
  Preserve the existing owner, accepted decisions and approval boundaries.
  A small Repair needs no new planning flow; a missing skill is not a reason
  to install it or block an otherwise qualified existing route.
- On accepting a Handback, advance it to review, Repair or authorized
  integration. If work must wait, record the next owner and the condition that
  lets it resume in the existing task.
  Keep the candidate revision, last proved state, evidence pointers and next
  action together there so recovery does not require replaying conversation.
- At dispatch, reassignment and Handback, keep the worker visibly associated
  with its current project and assignment in the existing execution labels
  and owning task. Refresh assignment names when work changes; leave status
  reporting with the runtime owner.
- Before dispatch, check the existing task, active worker and current PR for
  overlapping work. Continue with the existing owner, or state why a separate
  assignment is needed.
- When the same finding survives a Repair attempt, diagnose the cause and
  revise the brief before another attempt. Use the existing retry limit;
  escalate only when a material decision or authority is missing.

## Improve the next task

At a meaningful delivery handback or when the same friction recurs, ask:
**How can I modify the environment to improve the outcome of the next task?**

- Base the answer on observed friction, a user correction or a failed check.
  Name the next task that benefits and the evidence that makes the change useful.
- Prefer one small improvement to an existing instruction, interface, check or
  data-access route. Give it an owner, a bounded change and a completion check.
  Reuse the existing mechanism before proposing another tool or process.
  For a new deterministic check, use the installed `test-design` skill's
  negative-control procedure: show it rejects the observed failure and accepts
  the supported case. A green exit with no relevant execution is not proof.
- Make the improvement within current authority when it is necessary to satisfy
  the current task, or when an existing improvement mandate covers it and it
  will not delay ready delivery. Otherwise record the proposal with the project
  owner and continue delivery. "No change needed" is a valid result.
- Infrastructure work needs a named delivery blocker, the smallest supported
  remedy and a stop condition that returns work to delivery. General cleanup,
  speculative hardening and repairing third-party tools require their own scope.
  A strategic review does not expand approval or maintenance authority.

## Retain useful knowledge

- Keep durable decisions, corrections and recurring friction in the existing
  project knowledge owner. Update the affected note and its existing navigation
  when needed; create a page only for a distinct topic. Keep raw logs and worker
  receipts with the execution owner and cite them.
- Date historical claims and bind code evidence to a repository and commit.
  Preserve superseded decisions with a successor link. Refresh live task, code
  and forge state before acting; retained memory is context, not live proof.
- During normal closeout or recovery, repair contradictions and broken pointers
  in the notes being used. Broader knowledge audits and recurring checks need a
  demonstrated delivery benefit and the existing scheduling authority; reuse a
  matching schedule rather than creating another watcher.
